## Цель после обследования

Debian 13.7, hostname `debian13-new`, 2 vCPU, 4 ГиБ RAM, диск
60 ГиБ (около 56 ГиБ доступно), DHCP IP `192.168.1.162`, SSH/22;
VM работает, автозапуск включён, failed systemd units нет.
Эти сведения пока не сверены входом на VM/Proxmox. Выделенная VM
соответствует предложенным CPU/RAM/диску; для пилота по-прежнему
нужны отдельные code/state/backup/logs, один ASGI-процесс и один
вычислительный child. Целевые p95/RSS ещё не измерены.

VM109 (`geoai-dev`): Debian 13.7, 2 vCPU, 3.9 ГиБ RAM, около 50 ГиБ
свободно; занята разработкой и loopback тестовыми серверами. CT108
(`mcp-ops`): Debian 13.6, 2 vCPU, 4.0 ГиБ RAM, около 24 ГиБ
свободно; работают NetBird, почта и MCP-ops. Docker на этих узлах не
обнаружен. Существующие Compose, Dockerfile и workflow `main`
публикуют Telegram-бота, не web-пилот. Рабочий хост бота из доступных
документов не установлен; его не используем и не обследуем через секреты.
Место на диске учитывает квоты владельца 512 МиБ основных файлов
и 256 МиБ эталонов, результаты, журналы и отдельную резервную копию.

Доступ после разрешения: частный HTTPS через согласованный VPN
(например, NetBird) и список пилотных клиентов, без публичного маршрута.
Приложение связывается только с `127.0.0.1:18460`; Caddy TLS proxy на той же
VM слушает только VPN-интерфейс. Имя, сертификат и правила доступа ещё
не назначены, поэтому сетевой шаг сейчас не выполняется. Один заранее
созданный владелец и две его браузерные сессии; работу двух живых
разных владельцев выпуском не подтверждали. Бот, его токен и SQLite
не используются.

### Фактический доступ к Proxmox и VPN

На CT108 NetBird 0.81.2 подключён как `mcp-ops.netbird.cloud`,
`100.104.140.204/16`; видны два peer: `desktop-l4bb2vp.netbird.cloud`
(`100.104.97.169`) и `openclawagent.netbird.cloud` (`100.104.100.176`).
У CT108 нет назначенных NetBird Networks. Имя `pve1.netbird.cloud`
разрешается в `100.104.86.94`, но из CT108 SSH/22 отвечает
«No route to host», API/8006 недоступен. На Windows нет активного
NetBird-интерфейса и маршрута к `100.104.86.94`; TCP 22/8006
недоступны. VM109 не подключена к NetBird. Доступного Proxmox API/SSH
инвентаря нет. Это результаты обследования **до полученной ниже
выписки владельца о созданной VM 110**; состояние других ресурсов,
постоянство DHCP IP и адресный план напрямую не проверены.
Оставшаяся read-only проверка: на Proxmox
`pvesh get /cluster/resources`, `pvesh get /cluster/nextid`, сведения
о storage и утверждённый адресный план/DHCP либо эквивалентная
выгрузка от администратора.

После разрешения Caddy завершает TLS только на назначенном NetBird IP.
Внутренний CA выдаёт сертификат с SAN точного VPN DNS-имени VM;
разрешённые клиенты получают доверие к этому CA. Шаблон Caddy
отключает HTTP redirect. Имя, IP, сертификат и клиенты пока не
назначены, сетевые правила не менялись.

### Полученная выписка о VM 110 и новые ограничения

Владелец сообщает: `geo-admin` имеет парольный вход и sudo,
`openclaw` — только вход по SSH-ключу; реквизиты находятся в
Vaultwarden, в репозиторий не передавались. Swap не настроен,
nftables firewall не настроен, публичного DNS, reverse proxy и
NetBird на VM нет. **VM 110 не включена ни в одно расписание
Proxmox backup.** Её текущий DHCP IP не является подтверждённым
постоянным адресом. С Windows TCP/22 отвечает; доверенного host key
для `192.168.1.162` в `known_hosts` нет, поэтому вход не выполнялся.
Для начала пилота требуются проверенный host key/SSH-доступ,
согласованное закрепление адреса и VPN/TLS-доступ, а также внешняя
относительно VM резервная копия с проверенным восстановлением.
Отсутствие swap учитывается при целевом тесте памяти/OOM;
само по себе оно не доказывает необходимость изменения VM.
Ничего из перечисленного сейчас не настраивалось.

## Данные, версия схемы и откат

Для нового пустого пилотного хранилища перенос **не нужен**. Проверить
пустоту корней до первого старта; не копировать рабочую БД Telegram,
съёмку или секреты. Приложение создаёт auth SQLite `user_version=1`
и projects SQLite `user_version=8`. Ранее в 039 плане ошибочно
упоминалась «schema v5»: это `schemaVersion` манифеста синтетического
staging, **не** версия проектной SQLite. Предыдущий принятый P6
`1ea061c1afb4b75b0aba06ae67d402b0a3e815a6` тоже понимает
проектную v8; переключение на копии сохранило владельца, исходник
и DXF. При таком откате справочник 029 исчезнет.

Если позднее понадобится миграция: сначала отдельное разрешение и
список данных/прав; консистентная offline-копия, SHA и
`PRAGMA quick_check`, восстановление в пустой корень, пробный переход
и обратное чтение на **копии**. Не открывать рабочую БД новой версией
до проверки отката. Несовместимость означает остановку записей и
возврат проверенной домиграционной копии в новый корень, без
непроверенной обратной миграции.

## После отдельного разрешения: запуск, наблюдение, остановка

1. Человек подтверждает VM/оператора, клиентов, DNS/TLS, данные,
   окно, хранение backup и пороги таблицы. Без этого — стоп.
2. Оператор проверяет ресурсы/пустые пути, доставляет точный архив
   79528bb, отдельный архив `pilot_ops` и lock, сверяет происхождение,
   размеры и SHA-256 обоих компонентов по итоговому манифесту.
   Разворачивает отдельные code/state/backup/logs, service user,
   адаптер и TLS proxy. Автоматический gate
   отвергает чужие хеши, версии, пути и права.
3. Оператор запускает один loopback-сервис и частный HTTPS; создаёт
   пилотного владельца по согласованному секретному каналу.
   Автопроверки: health=200, private anonymous=401, TLS, SQLite
   версии 1/8, отсутствие публичного listener, один worker.
4. Сначала разрешённые синтетические данные. Собирать p95 API/job,
   5xx/4xx, очередь, RSS server+child, CPU, swap, место, TLS/health.
   Автоматический monitor может уведомить/остановить по OOM, диску,
   памяти и health; оценка DXF, права на данные и go/no-go — человек.
5. Для остановки закрыть новые запросы, по утверждённому правилу
   завершить или отменить задания, остановить сервис и child.
   Потом offline backup SQLite с WAL/SHM и файлов, SHA-манифест,
   `PRAGMA quick_check` и пробное восстановление в **новый** корень.
   Удаление/сохранение пользовательских материалов решает человек.
6. Для code rollback после остановки переключить на совместимый P6,
   проверить health/владельца/хеши на копии. При повреждении или
   несовместимости — вернуть проверенную backup в новый корень.
   Не затирать единственную копию. Решение об откате и повторном
   открытии доступа принимает ответственный человек.

Журналы не содержат пароли, токены, тела запросов и координаты.
Ни один из перечисленных операционных шагов сейчас не выполнен.
