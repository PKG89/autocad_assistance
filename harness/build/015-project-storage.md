# GEOAI-015 — versioned project storage

## Scope and persistence contract

Add a framework-independent, separate project store under an explicit
server-owned root. Use SQLite from the standard library for metadata and
immutable files under UUID-named directories for source/result bytes. The store must not use
or migrate the Telegram statistics database. A project has a server UUID
and a display name; every source revision stores the exact accepted upload
bytes, SHA-256, format, explicit CRS/units/settings, parent revision and
algorithm version. No coordinate conversion or inferred unit/CRS.

Register calculation job IDs and their exact request/settings digest against
a revision. A successful result records its SHA-256, size, algorithm version
and relation to source/job. Preserve old revisions and results. The store
must be restart-safe, transactionally avoid metadata pointing at missing
files, and reject tampered files by digest. Source limit is the existing
10 MiB; result limit is the existing 25 MiB. Revision and job settings
are each capped at 64 KiB of canonical JSON. All paths are generated by
the server. The feature remains service-only until 016–017 supply identity
and ownership checks, and 019–020 supply web routes.

Candidate files: `services/project_store.py`, a narrow public byte
validation helper in `services/uploads.py` for rechecking copied sources,
focused service tests and task memory. Keep 014 coordinator and synchronous HTTP/
Telegram paths unchanged. No production DB, `.env`, real surveys,
authentication shortcut, external database, deployment or system install.

## Acceptance and checks

1. Create a project and multiple immutable source revisions from validated
   upload IDs. Store exact bytes, digest, declared format, settings and
   parent/version sequence. Restart preserves all data; older revisions
   remain readable after later writes.
2. Register a job and publish a verified result for its revision. The
   result points to the source and parameter digest and can be read after
   restart. Wrong status, altered bytes or mismatched digest is rejected.
3. Unknown UUIDs, symlinks and altered metadata cannot escape the root or
   read unrelated files. Partial file/database failures leave no accepted
   revision or result. No public unauthenticated project endpoint.
4. Run focused tests, current isolated regression/API suites, negative
   tamper and rollback checks, `pip check`, and `git diff --check`.
